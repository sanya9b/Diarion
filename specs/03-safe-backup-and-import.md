# 03 — Безпечний бекап та імпорт

- **Priority:** P0 · **Effort:** M · **Status:** Done · **Depends on:** 01 · **Blocks:** 12

## Продукт

**Проблема.** Поточний імпорт бекапу може **безповоротно знищити всі дані користувача** одним хибним файлом,
а експортовані бекапи — незашифровані копії, що течуть у хмару/пошту, порушуючи «local-only». Для
локального застосунку без хмари бекап — єдина стратегія відновлення, тож його крихкість критична.

**Конкуренти.** Day One/Journey валідують і шифрують експорт; імпорт ніколи не перезаписує наживо без
резервної копії. «Ваші дані, портативні та ваші» — очікуваний стандарт.

**Цінність.** Робить локальну модель безпечною й надійною; знімає ризик тотальної втрати; підсилює
privacy-позиціонування (зашифрований бекап).

**User story.** *Як користувач, я хочу відновитися з бекапу без ризику втратити поточні дані, і бути певним,
що мій експортований файл ніхто не прочитає без мого пароля.*

## Інженерія

### Проблема / докази
- `Diarion.Core/Services/BackupService.cs:80-85` — імпорт робить `_dbContext.Close()` + `File.WriteAllBytes(dbPath, bytes)`:
  **без валідації**, без резервної копії, без rollback. Picker (`:56-66`) приймає `application/octet-stream`
  і `application/x-sqlite3` — тобто довільні/чужі (не LiteDB) файли.
- `Diarion.Core/Services/BackupService.cs:84` — коментар «Next call to GetCollection will automatically re-open
  the DB» **хибний**: після `Close()` `_db=null`, а `DatabaseContext.GetCollection` (`DatabaseContext.cs:63-64`)
  кидає `InvalidOperationException`, а не перевідкриває. Тобто після імпорту БД мертва до перезапуску.
- `Diarion.Core/Services/BackupService.cs:31-38` — експорт копіює можливо-відкритий файл БД у **спільний**
  `FileSystem.CacheDirectory` і **не видаляє** temp; копія відкрита (незашифрована) і без checkpoint логу.

### Вимоги (Requirements)
**Імпорт (validate → backup → atomic swap → reopen):**
- **R1.** Записати вибрані байти у temp-файл у приватній теці (не поверх живої БД).
- **R2.** **Валідувати** temp як справжню Diarion-БД: відкрити `new LiteDatabase(<connstr із паролем>)` у
  try/catch і перевірити наявність очікуваних колекцій (напр. `DatabaseConstants.EntriesCollection`) та
  сумісність `SchemaVersion` (координація зі spec 12); dispose. При невдачі — **abort**, жива БД недоторкана.
- **R3.** `Close()` живу БД, скопіювати поточний файл у `*.bak`, потім `File.Replace(temp, dbPath, bakPath)`
  (атомарний swap). На винятку — відновити з `*.bak`.
- **R4.** Додати `IDatabaseContext.Reopen()` (перезапуск `Initialize`) і викликати після swap; прибрати хибний коментар.
- **R5.** Увесь swap — під тим самим `_lock`, що й `Close`/`DropAllData`, і з обробкою `-log` sidecar (видалити стале).
- **R6.** FilePicker: приймати лише власне розширення (`.db`/`.diarionbak`); прибрати `x-sqlite3`/`octet-stream`
  або перевіряти вміст, а не MIME.

**Експорт:**
- **R7.** Перед копіюванням зробити checkpoint логу LiteDB (`Checkpoint()`), щоб бекап був консистентним.
- **R8.** **Шифрувати** експорт (пароль/парольна фраза користувача або той самий device-key зі spec 01, або
  окремий пароль для міжпристроєвого перенесення — обрати; за замовчуванням зашифровано).
- **R9.** Писати temp у приватну теку, а після `Share` — **видаляти** temp; не накопичувати копії в cache.
- **R10.** Ім'я/формат файлу з версією схеми в заголовку/маніфесті (для валідації при імпорті).

### Критерії приймання (Acceptance)
- **AC1.** Імпорт чужого/пошкодженого файлу → повертає `false`, показує помилку, **жива БД без змін** (дані на місці).
- **AC2.** Успішний імпорт валідного бекапу → дані замінені, `*.bak` створено, застосунок **працює без
  перезапуску** (`Reopen` спрацював).
- **AC3.** Виняток під час swap → автоматичне відновлення з `*.bak`, дані не втрачені.
- **AC4.** Експортований файл зашифрований (не читається як LiteDB без пароля/ключа) і консистентний
  (останні збережені записи присутні).
- **AC5.** Після експорту в cache/приватній теці **не лишається** незашифрованих temp-копій.

### Тест-план
- Unit: валідатор бекапу приймає справжню Diarion-БД і відхиляє чужу/пошкоджену.
- Unit/Integration (файлова): успішний swap + `Reopen`; збійний swap → rollback з `*.bak`.
- Unit: експорт створює зашифрований файл, який відкривається лише з ключем; temp видалено.
- Manual/E2E: повний цикл export→wipe→import на пристрої.

### Ризики / застереження
- Потрібне достатнє місце для temp + `*.bak` (2× розмір БД) — перевіряти вільне місце перед swap.
- Якщо шифрування експорту прив'язати до device-key (spec 01), бекап **не** відновиться на іншому пристрої —
  для міжпристроєвого сценарію передбачити окремий пароль користувача.
