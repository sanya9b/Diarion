# 12 — Версіонування схеми та міграції

- **Priority:** P1 · **Effort:** L · **Status:** Proposed · **Depends on:** 03 · **Blocks:** —

## Продукт

**Проблема.** Немає жодної стратегії версіонування схеми чи міграцій — еволюція моделі тримається виключно на
schemaless-толерантності LiteDB. Додавання полів «безпечне випадково», але будь-який rename/зміна типу/поділ
безшумно втратить чи неправильно прочитає дані, а відновлення старішого бекапу в новішу збірку не має гарда.
Це фундамент для безпечного розвитку **всіх** інших spec (шифрування-міграція, нові поля звичок/циклу/читання).

**Цінність.** Дає контрольований шлях апгрейду й міжверсійну сумісність бекапів; знімає приховану загрозу
мовчазної втрати даних при рефакторингу моделей.

**User story (dev/user).** *Як розробник, я хочу безпечно змінювати схему між релізами; як користувач — не
втратити дані при оновленні застосунку чи відновленні старого бекапу.*

## Інженерія

### Проблема / докази
- Немає поля/механізму версії схеми; `DatabaseContext.Initialize` (`DatabaseContext.cs:24-59`) лише створює
  колекції/індекси й сідить, без версіонування чи міграційного раннера.
- `Diarion.Core/Models/DiaryEntry.cs:66-76` містить «legacy» поля (`Title`, `Content`, `Emotion`, `AiSummary`),
  що вказує на неконтрольовану еволюцію моделі.
- Імпорт бекапу (spec 03) не перевіряє версію схеми відновлюваного файлу.
- Неузгоджені timestamp-и (`DateTime.Now` vs `UtcNow`, напр. `FinanceTransaction.cs:19`) + UTC-зберігання
  LiteDB → крайові кейси зсуву дати; варто нормалізувати в межах міграцій.

### Вимоги (Requirements)
- **R1.** Ввести `SchemaVersion` (метадокумент/спец-колекція, напр. `_meta`), що читається при старті.
- **R2.** Міграційний раннер: впорядкований набір міграцій `From→To`, що застосовуються послідовно при
  `db.Version < CurrentVersion`, у транзакції, з логуванням; кожна міграція ідемпотентна.
- **R3.** Структура `Migrations/` з окремими класами міграцій (напр. `M001_...`, `M002_...`).
- **R4.** Гард при імпорті (spec 03): якщо версія бекапу > поточної збірки — відхилити з поясненням; якщо
  менша — прогнати міграції після swap.
- **R5.** Прибрати/мігрувати legacy-поля `DiaryEntry` контрольовано (не «зависати» в half-state).
- **R6.** Нормалізувати timestamp-и та `Date` (координація зі spec 11 і з нормалізацією `DiaryEntry.Date`):
  єдина політика (напр. локальна дата без часу для day-keys; UTC для точних міток), закладена в міграцію.
- **R7.** Координація зі spec 01: одноразова міграція «відкрита→зашифрована» БД реєструється як крок у раннері.

### Критерії приймання (Acceptance)
- **AC1.** Свіжо створена БД має актуальний `SchemaVersion`; старт не запускає зайвих міграцій.
- **AC2.** БД зі старою версією апгрейдиться до поточної без втрати даних (тест на зафіксованому старому дампі).
- **AC3.** Імпорт бекапу новішої версії — відхиляється з повідомленням; старішої — мігрується коректно.
- **AC4.** Legacy-поля `DiaryEntry` або підключені, або видалені (немає «мертвих» після міграції).
- **AC5.** Міграції ідемпотентні (повторний запуск не ламає даних) і покриті unit-тестами.

### Тест-план
- Unit: раннер застосовує міграції по порядку; ідемпотентність; пропуск, коли версія актуальна.
- Integration (файлова): апгрейд зафіксованого старого дампа → усі дані на місці й у новій формі.
- Unit: гард версій при імпорті (новіша відхилена, старіша мігрована).

### Ризики / застереження
- Міграції на великих БД — виконувати з прогресом і в транзакції; передбачити резервну копію перед міграцією
  (переюзати `*.bak`-механізм зі spec 03).
- Помилкова міграція небезпечна — суворе тестування на реальних дампах перед релізом.
